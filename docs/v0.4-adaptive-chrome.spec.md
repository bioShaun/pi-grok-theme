# pi-grok-theme v0.4 — Adaptive Chrome Upgrade Spec

**Status:** Delivered in 0.4.0  
**Target version:** `0.4.0`  
**Date:** 2026-09-02  
**Target runtime:** Pi Coding Agent `>=0.80.0`, with progressive enhancement on newer UI APIs  
**Primary platforms:** Ghostty, WezTerm, iTerm2, Kitty, VS Code Terminal, modern Windows Terminal

> **Delivery note (2026-09-03):** All P0/P1 scope in §4 shipped in 0.4.0,
> including the §4.7 glyph vocabulary, §4.8 release gates, deterministic SVG
> previews, and the footer presets/theme switching originally tagged P1.
> §11's non-goals remain deferred (v0.5 appearance-aware switching, Oh My Pi
> theme variants as a separate distribution task, upstream schema proposals).
> Known limitation: theme switches made outside `/grok theme` recolor the
> cursor and spinner on the next session or `/grok theme` call, because Pi
> exposes no theme-change event. See `CHANGELOG.md` for the authoritative
> delivered/deferred split.  

## 1. Executive Summary

Version 0.4 should turn the existing static presentation layer into
**theme-native adaptive chrome**.

The release has five goals:

1. remove hard-coded dark-theme ANSI colors from the header, footer, and status
   rendering;
2. add Grok Build-style motion through a one-cell working spinner without
   destabilizing layout;
3. make context pressure and elapsed time more informative while preserving the
   one-line footer;
4. make `/grok theme` switch themes directly instead of only showing
   instructions;
5. add automated validation and visual release artifacts.

This is intentionally a focused release. It improves the surfaces users see on
every turn while avoiding high-risk editor replacement, raw-terminal probing,
or features for which Pi exposes no reliable state.

---

## 2. Evidence and Rationale

This spec synthesizes:

- `docs/theme-research.md`
- `docs/omp-theme-research.md`
- `docs/grok-build-ui-gaps.md`
- the current v0.3 implementation in `index.ts`, `footer.ts`, `header.ts`,
  `status.ts`, and `cursor.ts`

The strongest findings are:

- pi-grok-theme already leads the Pi community in theme-token coverage and
  theme-plus-extension integration;
- its main architectural weakness is that extension chrome uses hard-coded
  GrokNight ANSI colors, so `grok-build-day` cannot fully control its own
  presentation;
- Grok Build's highest-value, low-cost visual traits are a stable one-column
  spinner, compact token notation, context-pressure coloring, and explicit
  phase/turn timing;
- Oh My Pi's most transferable product idea is configurable status-line
  presentation, but a full 24-segment clone would be excessive for upstream Pi;
- the strongest community theme packages invest in screenshots, schema checks,
  and CI, areas where this repository currently trails.

## 3. Product Principles

### 3.1 Theme-native, not GrokNight-hard-coded

All in-TUI text styling must come from Pi's active `Theme` object. Dark and light
themes must render correctly without maintaining duplicate ANSI constants.

The only allowed fixed RGB values are terminal-control values that Pi's theme
API cannot expose directly, such as OSC 12 cursor colors.

### 3.2 Motion must communicate state

Animation is reserved for active work. Idle state remains still. No perpetual
decorative animation should consume attention or trigger needless renders.

### 3.3 One line is the default contract

The footer remains a single line at every terminal width. New information must
participate in a deterministic priority and dropping system.

### 3.4 Honest metrics only

Only display values available from real Pi runtime data. Do not restore the
withdrawn turn-average tok/s metric until Pi exposes a trustworthy timing/data
path.

### 3.5 Progressive enhancement

Newer optional Pi UI APIs must be feature-detected. On older supported Pi
versions, the extension must retain v0.3 behavior rather than fail startup.

## 4. Scope

### 4.1 P0 — Theme-native chrome

Replace formatting based on `ANSI_COLORS` with formatting based on the active
Pi `Theme` instance.

Affected surfaces:

- footer segments and separators;
- status badge;
- optional header;
- `/grok` notifications where practical;
- working-indicator frames.

Required semantic mappings:

| UI role | Pi theme token |
|---|---|
| Primary active value | `text` |
| Secondary metadata | `muted` |
| Separators and inactive values | `dim` |
| Branch and active model emphasis | `accent` |
| Running tool | `warning` |
| Success/healthy state | `success` |
| Critical context pressure | `error` |
| Thinking state | `thinkingText` or the active thinking-level token |

Implementation direction:

- make `WorkingStateController` return semantic badge data, not preformatted
  ANSI text;
- introduce a small chrome styling adapter around `Theme.fg()`, `Theme.bold()`,
  and `Theme.getFgAnsi()`;
- pass the `Theme` received by `setFooter` and `setHeader` into render
  functions;
- retain ANSI reset handling only inside the adapter;
- remove `ANSI_COLORS` as the source of UI colors. A compatibility export may
  remain during migration only if existing public imports require it.

#### Cursor color

OSC 12 remains outside the Pi theme API. Use a named-theme cursor map:

| Theme | Cursor |
|---|---|
| `grok-build-coding` | `#E0AF68` |
| `grok-build` | `#E0AF68` |
| `grok-build-day` | `#B45309` |
| Unknown/third-party theme | do not override, or restore terminal default |

Changing the active theme through `/grok theme` must immediately apply the
matching cursor policy.

### 4.2 P0 — Stable Grok working indicator

Use `ctx.ui.setWorkingIndicator()` when available.

Default frames:

```text
⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧
```

Requirements:

- every frame must have visible width exactly 1 according to `pi-tui`;
- default interval: `120ms`;
- frame color must come from the active theme's `accent`;
- legacy fallback frames: `| / - \`;
- restore Pi's default indicator on `session_shutdown`;
- reapply colored frames after a theme switch;
- feature-detect `setWorkingIndicator`; absence must not produce an error.

The footer may retain a compact static state marker. It must not duplicate a
second animated spinner.

### 4.3 P0 — Context pressure metric

Adopt Grok Build's compact token vocabulary and clearer pressure thresholds.

Wide form:

```text
⇣48k/200k (24%)
```

Compact form:

```text
24%
```

Threshold mapping:

| Context use | Token |
|---|---|
| `< 65%` | `muted` |
| `65–79%` | `accent` |
| `80–89%` | `warning` |
| `>= 90%` | `error` |

Requirements:

- preserve the host-provided percentage when present;
- otherwise compute `usedTokens / totalTokens`;
- clamp display to `0–100%`;
- do not render a fabricated `0%` when usage is unavailable;
- `⇣` must fall back to `↓` in legacy glyph mode;
- truncation must never leave a dangling ANSI sequence or exceed terminal
  width.

### 4.4 P0 — Coalesced render clock and dual timing

The current duration changes only when another Pi event requests a render.
Introduce a lifecycle-owned render clock.

Requirements:

- while an assistant turn is active, request at most one render every `250ms`;
- stop the clock when the turn ends or the session shuts down;
- never create more than one active timer;
- call `unref()` when supported so the timer cannot keep Node alive;
- high-frequency `message_update` events should mark the footer dirty rather
  than force an unbounded render per token;
- expose both:
  - **phase elapsed:** time since thinking/streaming/tool state began;
  - **turn elapsed:** time since the assistant turn began.

Default footer behavior:

- normal widths show phase duration in the status label;
- the `full` preset may additionally show total turn duration;
- compact mode drops total turn duration first.

### 4.5 P1 — Footer presets

Provide a small configuration model inspired by Oh My Pi without cloning its
full status-line subsystem.

Built-in presets:

| Preset | Segments |
|---|---|
| `auto` (default) | Existing responsive hierarchy with all eligible segments |
| `minimal` | model · context · status |
| `full` | cwd · branch · model · context · thinking · turn time · extension statuses · status |

Commands:

```text
/grok footer
/grok footer auto
/grok footer minimal
/grok footer full
```

Requirements:

- `/grok footer` reports the current preset and available values;
- preset changes apply immediately;
- all presets keep status and model as their highest-priority core fields;
- third-party extension statuses remain supported;
- extension statuses are lower priority than status/model and must never force
  core fields off-screen;
- v0.4 may keep the selected preset session-local. Persistence is deferred
  unless Pi exposes a package-scoped settings API.

### 4.6 P1 — Direct theme switching

Upgrade `/grok theme` from an instruction page to an operational command.

Commands:

```text
/grok theme
/grok theme coding
/grok theme minimal
/grok theme day
/grok theme <installed-theme-name>
```

Behavior:

- no argument lists available themes using `ctx.ui.getAllThemes()` and marks the
  active theme;
- aliases resolve to the three bundled themes;
- a valid name calls `ctx.ui.setTheme(name)`;
- success reapplies the cursor policy, working-indicator colors, header, and
  footer;
- failure displays the returned error and preserves the current theme;
- command argument completion returns aliases and installed theme names;
- APIs are feature-detected; older Pi versions fall back to the existing
  instructions.

#### Explicit non-requirement

Autocomplete-hover live preview is not required. Pi's
`getArgumentCompletions()` returns candidates but does not expose a supported
preview/cancel lifecycle. Do not simulate preview by switching themes during
completion.

### 4.7 P1 — Legacy glyph mode

Add one central glyph table rather than scattering Unicode literals.

Required keys:

- working dot;
- idle circle;
- thinking mark;
- branch mark;
- token arrow;
- lightning/brand mark;
- disclosure arrow;
- spinner frames.

Activation:

- force with `PI_GROK_LEGACY_GLYPHS=1`;
- automatically use legacy mode on `win32` when neither Windows Terminal nor a
  known modern terminal is detected;
- allow `PI_GROK_LEGACY_GLYPHS=0` to override automatic detection.

All normal and fallback glyphs used in fixed-width chrome must have explicit
width tests.

### 4.8 P1 — Release quality and previews

Add release gates:

1. CI runs tests on current Node LTS and the runtime used by Pi;
2. all three theme JSON files are checked against Pi's theme schema;
3. all required and optional theme tokens remain explicitly present;
4. dark/day contrast checks cover primary text, muted text, errors, warnings,
   and diff colors on their relevant surfaces;
5. footer width tests cover widths `20–160`, all presets, active states,
   extension statuses, and both glyph modes;
6. screenshots are added for:
   - `grok-build-coding`;
   - `grok-build`;
   - `grok-build-day`;
   - narrow and wide footer layouts.

Screenshots must be produced from a real Pi session or a deterministic renderer,
not hand-drawn text art.

## 5. Proposed Architecture

```text
index.ts
  ├─ lifecycle ownership
  ├─ command registration
  ├─ render clock
  └─ theme-switch side effects

chrome-theme.ts          (new)
  └─ semantic Theme-based formatting adapter

glyphs.ts                (new)
  ├─ modern glyph table
  ├─ legacy glyph table
  └─ terminal capability selection

footer.ts
  ├─ pure segment construction
  ├─ preset selection
  ├─ priority/drop fitting
  └─ Theme-based rendering

status.ts
  ├─ activity state machine
  ├─ phase + turn clocks
  └─ semantic badge model

cursor.ts
  ├─ named-theme cursor policy
  └─ OSC 12 / OSC 112 transport

header.ts
  └─ Theme- and glyph-aware rendering
```

### 5.1 Semantic status model

`WorkingStateController` should expose data similar to:

```ts
interface StatusBadge {
  state: AgentActivityState;
  icon: GlyphKey;
  tone: "muted" | "accent" | "thinking" | "warning";
  label: string;
  phaseElapsedMs?: number;
  turnElapsedMs?: number;
}
```

It must not embed ANSI escape codes. Rendering belongs to the chrome adapter.

### 5.2 Pure footer model

Footer fitting should operate on segments with metadata, not compare formatted
strings by identity:

```ts
interface FooterSegment {
  id: string;
  priority: number;
  required: boolean;
  wide: string;
  compact?: string;
}
```

The fitting algorithm should:

1. render wide variants;
2. remove optional segments from lowest to highest priority;
3. replace eligible segments with compact variants;
4. preserve required model/status segments where data exists;
5. truncate only as a final safety net.

### 5.3 Timer ownership

Only `index.ts` owns intervals. Renderers and state objects must not create
timers. This guarantees cleanup and keeps pure rendering deterministic in tests.

## 6. Detailed Responsive Priority

Highest priority first:

1. active status;
2. model;
3. branch;
4. context percentage;
5. third-party extension status;
6. thinking level;
7. turn duration;
8. cwd.

Fitting rules:

- status is never deliberately dropped;
- model is retained whenever present;
- wide context becomes compact percentage before being dropped;
- third-party extension statuses must be individually droppable;
- cwd is always the first standard segment removed;
- at widths too small for complete required fields, truncate the lowest-priority
  required field before the status marker;
- every returned line must satisfy `visibleWidth(line) <= width`.

## 7. Lifecycle Requirements

### Session start

- reset stale state;
- apply cursor policy for the active theme;
- install footer and optional header;
- install the working-message wrapper;
- configure the custom working indicator when supported;
- set title and hidden-thinking label;
- do not start the render clock while idle.

### Turn/message start

- initialize turn and phase timestamps;
- start the render clock exactly once;
- request an immediate render.

### Tool start/end and message update

- update state synchronously;
- mark chrome dirty;
- allow the render clock to coalesce updates.

### Message/turn end

- record final elapsed values;
- stop the render clock;
- clear the host working message with `undefined`;
- request one final render.

### Session shutdown

- stop all timers;
- restore the original `setWorkingMessage`;
- restore Pi's default working indicator;
- reset OSC 12 cursor color;
- dispose footer and header;
- leave title and hidden-thinking label ownership to Pi core, matching v0.3
  behavior.

All cleanup operations must be idempotent.

## 8. Acceptance Criteria

### AC-01 — Theme-native rendering

- No footer/header/status foreground color is sourced from a fixed dark-theme
  RGB constant.
- Switching from `grok-build-coding` to `grok-build-day` recolors chrome
  immediately.
- Third-party themes remain legible because semantic Pi theme tokens are used.

### AC-02 — Working indicator

- Active work uses the configured one-column spinner on supported Pi versions.
- Legacy mode uses `|/-\`.
- Indicator setup and teardown do not throw when the API is absent.
- No spinner remains customized after shutdown.

### AC-03 — Context metric

- Wide output uses `⇣used/total (percent%)`.
- Compact output uses percentage only.
- Threshold colors transition at 65%, 80%, and 90%.
- Missing context data renders no context segment.

### AC-04 — Timing correctness

- Phase time resets on each activity-state transition.
- Turn time does not reset until the assistant turn ends.
- Active duration updates without requiring token/tool events.
- No interval remains after turn end or shutdown.

### AC-05 — Width safety

- For every tested width from 20 through 160, all presets and states return one
  line whose `visibleWidth` does not exceed the width.
- ANSI sequences remain balanced after fitting and truncation.
- Extension statuses cannot cause Pi TUI overflow.

### AC-06 — Theme command

- `/grok theme day` activates `grok-build-day` without requiring `/settings`.
- An unknown theme leaves the current theme unchanged and reports a warning.
- Completion includes bundled aliases and currently installed themes.
- Older Pi versions receive the existing manual-switch guidance.

### AC-07 — Compatibility and teardown

- Existing v0.3 commands remain valid.
- Header remains opt-in.
- OSC 112 is emitted on shutdown if this extension set the cursor.
- Repeated session setup/shutdown does not stack wrappers, timers, or footer
  subscriptions.

### AC-08 — Release gate

- Unit tests, type checking, theme-schema validation, and contrast checks pass in
  CI.
- Real or deterministic screenshots for all three themes are committed and
  linked from both READMEs.

## 9. Test Plan

### Unit tests

- semantic state transitions and phase/turn timestamps using an injected clock;
- context formatting at `undefined`, 0, 64, 65, 79, 80, 89, 90, and 100%;
- glyph width for modern and legacy sets;
- cursor policy by theme name;
- preset segment membership and priority;
- fitting/property loop across widths 20–160;
- shutdown idempotency and timer cleanup;
- theme switching success/failure and API absence.

### Integration-style tests with fake Pi context

- `setWorkingIndicator` receives expected frames and reset call;
- `setTheme` success triggers rerender and cursor update;
- repeated `session_start` does not double-wrap `setWorkingMessage`;
- `message_update` bursts produce bounded render requests;
- all existing `/grok` subcommands continue to work.

### Manual validation

Test in:

- one dark truecolor terminal;
- one light terminal session;
- tmux;
- Windows Terminal or forced legacy glyph mode;
- widths around critical boundaries: 20, 40, 60, 79, 80, 100, 120.

## 11. Explicit Non-goals

The following are not part of v0.4:

- replacing Pi's editor to change the prompt arrow;
- raw OSC 11 stdin probing;
- cross-platform system appearance polling or automatic light/dark switching;
- animated idle monitor or "waiting on you" pulse without a reliable Pi event;
- tok/s, cost, subagent, watcher, todo, permission, or PR segments whose source
  data is unavailable or belongs to another extension;
- per-heading h1–h6 colors, which require a Pi theme-schema change;
- a BtwBlock side-question panel, timeline, session picker, mouse layer, or Vim
  editor;
- Oh My Pi-compatible theme artifacts in the main Pi package.

These may be considered in later releases:

- **v0.5:** appearance-aware dark/light switching after a safe detection design;
- **separate distribution task:** generated Oh My Pi theme variants;
- **upstream proposals:** per-heading colors, symbol presets, and themeable
  status-line tokens.

## 12. Success Metrics

The release is successful when:

- `grok-build-day` chrome is visually native rather than dark-theme ANSI pasted
  onto a light canvas;
- active work is recognizable from a stable one-cell Grok-style spinner;
- users can understand context pressure and phase duration without opening
  another view;
- users can switch bundled themes directly with one command;
- no tested footer width can crash Pi's strict TUI width validation;
- repository previews and CI make the package easier to evaluate and safer to
  release.
